# Course map: each research question, answered in code

Each section gives the research question, how this system answers it, where to look, and something to try.

---

## Week 1 · Evolution of service-oriented software engineering
**Why did SOA evolve, and what problems does each generation solve?**
See `docs/architecture.md §1`. The repo runs in three modes that mirror the evolution: one process
(`scripts/devstack.py`), containers (`docker-compose.yml`), and cloud-native (`deploy/helm`, Istio, KEDA, Knative,
Dapr). The code is identical in all three. Only configuration changes (`EVENT_BUS`, `*_DATABASE_URL`,
`RESILIENCE_MODE`), which is the twelve-factor principle that made cloud-native possible.

## Week 2 · Microservice architecture: principles, patterns, anti-patterns
**When do microservices improve a system, and when do they make it worse?**
* Patterns: database per service, API gateway, BFF (`GET /api/v1/bff/tweets/{id}`), service chassis
  (`twitter_common/service.py`), health-check API, externalised config, and a routing table that would allow
  strangler-fig migration (`api_gateway/main.py: ROUTES`).
* They improve things here because the read path (timeline/search) scales independently of the write path, and
  engagement needs an audit log that the rest of the system does not.
* They make things worse in the price we pay: eventual consistency, 12 deployables, the need for tracing. For a
  hobby-sized Twitter, a modular monolith would be cheaper; see the anti-pattern table in `architecture.md §4`.

## Week 3 · API engineering & service contracts
**How should modern services expose and evolve their interfaces?**
* **Contract-first gRPC:** `proto/twitter_protos/user/v1/user.proto` → `make proto`. `buf.yaml` + CI run
  `buf breaking` on every PR.
* **REST/OpenAPI:** generated by FastAPI and exported to `contracts/openapi/`; CI fails if they drift.
* **Events:** `contracts/asyncapi.yaml` is generated from the pydantic event models; event types are versioned
  (`tweet.created.v1`).
* **Evolution:** `GET /v1/tweets/{id}` returns `Deprecation`, `Sunset` and `Link: rel="successor-version"`
  headers, and `GET /v2/tweets/{id}` reshapes the resource. The tolerant reader is
  `CloudEvent(model_config extra="ignore")`.
* **GraphQL** (`api_gateway/graphql_api.py`): the client chooses the shape; the DataLoader turns N author lookups
  into one gRPC call.

Try it: compare `curl -i localhost:8000/api/v1/tweets/<id>` with `/api/v2/tweets/<id>`.

## Week 4 · Event-driven architecture
**How does asynchronous communication change service-oriented systems?**
Producers (`user`, `tweet`, `engagement`, `ai-agent`) publish CloudEvents to per-aggregate topics, keyed by
aggregate id for ordering. Consumers subscribe with their own consumer group. Consequences you can observe:
* **Temporal decoupling:** set chaos on timeline-service and keep tweeting; the timeline catches up afterwards.
* **Extensibility:** notification-service and the AI moderator were added without touching any producer.
* **New failure modes:** duplicates (handled by the inbox), poison messages (retries with backoff, then a DLQ topic
  `<topic>.dlq`), and eventual consistency.

Code: `twitter_common/events.py`, `twitter_common/bus.py`.

## Week 5 · Distributed transactions & data consistency
**How can consistency be maintained without distributed ACID transactions?**
* **Transactional outbox** (`twitter_common/outbox.py`): the business row and the event are written in one local
  transaction; a relay publishes them. This avoids two-phase commit and the dual-write problem.
* **Idempotent consumer / inbox:** `claim_event()` records the event id in the same transaction as the side effect,
  so at-least-once delivery has an effectively-once effect.
* **Saga** for multi-service invariants (Week 6).
* **Optimistic concurrency** in the event store (`(stream_id, version)` primary key, retry on conflict).

## Week 6 · Saga, CQRS and Event Sourcing
**How do modern patterns solve transaction and state-management problems?**
* **Saga** (`saga_orchestrator/main.py`): 4 steps with compensations and a pivot (`send_welcome` is retriable,
  never compensated). The saga log is persisted, and **recovery on start-up** compensates sagas interrupted by a
  crash. `test_saga_compensates_when_a_later_step_fails` makes step 3 fail and asserts that steps 2 and 1 were
  undone.
* **CQRS** (`timeline_service`): the write model lives in tweet/user/engagement services and the read model is a
  denormalised projection fed by events. It also implements the hybrid push/pull fan-out.
* **Event sourcing** (`engagement_service`): an append-only event store per tweet, state rebuilt by folding events,
  snapshots every 50 events, **temporal queries** (`?as_of_version=N`) and the raw stream
  (`/engagement/events`).
* **Projection rebuilt from the log:** search-service has no database; it replays the topics on start-up.

## Week 7 · Orchestration vs choreography & business processes
**When should services be centrally orchestrated versus coordinated through events?**

| | Orchestration (registration) | Choreography (account deletion, notifications, moderation) |
|---|---|---|
| Who decides the flow | `saga-orchestrator` | Each participant reacts to `user.deleted`, `tweet.created`, … |
| Visibility | One place: `GET /api/v1/sagas/{id}` shows every step | Spread across services; needs tracing |
| Coupling | Orchestrator knows every participant | Producers know nobody |
| Failure handling | Explicit compensation order | Each consumer retries independently |
| Best when | Ordered steps, must undo on failure, business wants a process view | Independent reactions, many consumers, extensibility |

The saga log (`saga_instances`, `saga_steps`) is a minimal BPM process engine: process instances, step history,
status, recovery.

## Week 8 · Service mesh
**Should communication, security and observability be handled by the application or the infrastructure?**
This system implements both so they can be compared:

| Concern | Application level (`twitter_common`) | Infrastructure level (`templates/istio.yaml`) |
|---|---|---|
| Retries / timeouts | `retry_async`, `ResilientClient` | VirtualService `retries`, `timeout` |
| Circuit breaking | `CircuitBreaker` | DestinationRule `outlierDetection` |
| Bulkhead | `Bulkhead` | DestinationRule `connectionPool` |
| Service identity | JWT client credentials | SPIFFE identities + STRICT mTLS |
| Authorization | Scopes on `/internal/*` | AuthorizationPolicy (allowed callers) |
| Telemetry | OpenTelemetry SDK | Sidecar metrics/traces |
| Traffic shifting | — | Canary weights (`istio.canary`) |

`RESILIENCE_MODE=mesh` (the Helm default) disables app retries so that the two layers do not multiply into a retry
storm. Application-level identity stays on, giving defence in depth. Conclusion: put transport concerns in the
mesh, and keep the semantic ones (fallbacks, idempotency, business authorization) in the app.

## Week 9 · Cloud-native SOSE: containers, Kubernetes, serverless, Dapr
**How has cloud computing changed service-oriented engineering?**
* Containers: one parametrised, non-root image (`deploy/docker/Dockerfile`).
* Kubernetes: `deploy/helm/twitter`, with probes, rolling updates (`maxUnavailable: 0`), PDBs, topology spread,
  HPA/KEDA.
* **Serverless:** `functions/content-filter` as a Knative Service with scale-to-zero. tweet-service calls it through
  a circuit breaker and degrades gracefully when it is cold or failing.
* **Dapr:** `EVENT_BUS=dapr` makes services publish through the sidecar (`DaprEventBus`), and
  `deploy/dapr/components.yaml` swaps the broker and declares resiliency policies without code changes.

## Week 10 · Resilience engineering & self-healing
**How can distributed services detect failures and recover automatically?**
* Detect: timeouts, readiness probes, circuit-breaker failure counting, AIOps anomaly detection.
* Contain: bulkheads, circuit breakers that fail fast, rate limiting, load shedding.
* Recover: retries with jittered backoff, supervised background loops (`supervise()`), Kubernetes restarts on
  liveness failure, outbox relay resume, DLQ, saga crash recovery.
* Degrade: tweet-service falls back to JWT claims if user-service is down (`x-degraded` header), the BFF returns
  partial results, and AI features fall back to heuristics.
* **Chaos:** `PUT /internal/chaos {"error_rate":…, "latency_ms":…}` on any service. See
  `test_circuit_breaker_fails_fast_under_chaos`.

## Week 11 · Observability, distributed tracing & AIOps
**How can we understand and diagnose failures in highly distributed systems?**
* **Metrics:** RED metrics plus circuit state, outbox backlog, saga outcomes and adaptation mode
  (`twitter_common/observability.py`). Grafana dashboard and SLO alert rules are under `deploy/`.
* **Traces:** OpenTelemetry auto-instrumentation for FastAPI, httpx and gRPC, **plus trace context carried inside
  CloudEvents** (`traceparent` extension), so a trace continues across Kafka into every consumer. In Jaeger, a
  single "POST /v1/tweets" trace shows the gRPC call, the outbox publish and the timeline, search and notification
  consumers.
* **Logs:** JSON with `trace_id`, `span_id` and `correlation_id` (propagated via `x-correlation-id`).
* **AIOps** (`aiops_service`): scrapes the fleet, learns per-metric baselines (EWMA), flags z-score outliers above a
  floor, and uses the dependency graph to separate the **probable root cause** from its victims. It publishes
  `aiops.anomaly_detected` events, and the AI agent can explain the system state through the `get_system_health`
  tool.

## Week 12 · Security & zero trust
**How should identity, authorization and trust be managed between thousands of services?**
* **Identity:** users get RS256 JWTs (aud `twitter-api`). Each workload gets its own identity through OAuth2 client
  credentials (aud `twitter-internal`) and, in k8s, a ServiceAccount, which gives a SPIFFE identity for mTLS.
* **Verification everywhere:** every service validates tokens locally against the JWKS (cached, refreshed on unknown
  `kid` → key rotation via `POST /internal/keys/rotate`). The gateway check is only an early reject.
* **Least privilege:** scopes per client (`SERVICE_CLIENT_SCOPES`), `require_service("users:provision")` on internal
  endpoints, `authorize_grpc` on every RPC, AI tools run with the end user's token, and Istio AuthorizationPolicies
  list allowed callers.
* **Network:** STRICT mTLS, deny-all AuthorizationPolicy, default-deny NetworkPolicy.
* **Workload hardening:** non-root UID, read-only root FS, all capabilities dropped, secrets from k8s Secrets, no
  passwords persisted in the saga log.

## Week 13 · Self-adaptive, elastic & autonomous systems
**Can service-oriented systems dynamically adapt their architecture and resources?**
Yes, at three levels:
1. **Application MAPE-K** (`api_gateway/adaptation.py`): monitor latency and errors, analyse against the SLO, plan
   NORMAL/DEGRADED/CRITICAL with hysteresis, then execute by re-tuning the rate limiter, disabling enrichment
   (brownout) and shedding non-critical routes. The knowledge base is at `GET /api/v1/adaptation`.
2. **Architectural adaptation** (`timeline_service.AdaptiveFanout`): the push/pull boundary for "celebrities"
   moves at runtime based on measured fan-out latency, so the system changes its own data-flow architecture.
3. **Resource elasticity:** HPA on CPU, KEDA on Kafka consumer lag, and Knative scale-to-zero.

## Week 14 · AI-native SOA: agents, tool services & MCP
**How will AI agents change the concept of a "service" and service-to-service interaction?**
* **Service → tool:** capabilities are described (name, natural-language description, JSON schema) and
  **discovered at runtime** over MCP (`/mcp`), rather than hard-coded by a developer against an SDK.
* **Agent as orchestrator:** `POST /api/v1/ai/agent` lets Claude plan which tools to call and in what order. This is
  model-driven orchestration, a new point on the orchestration-vs-choreography spectrum from Week 7.
* **AI as an event consumer:** the moderation consumer reacts to `tweet.created` and emits
  `moderation.tweet_flagged`, which notification-service turns into a notification (choreography).
* **New concerns:** authority (tools act with the user's token, and side-effecting tools need `allow_actions`), cost
  and latency (effort settings, deterministic fallbacks), non-determinism (structured outputs for moderation), and
  safety (refusal handling with server-side fallback models).

Try it: `claude mcp add --transport http twitter http://localhost:8000/mcp --header "Authorization: Bearer $TOKEN"`,
then ask Claude "what's trending on my Twitter and who should I follow?"
